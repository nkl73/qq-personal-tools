# 手机发文件，电脑处理，再回到 QQ

适用于 v0.9.0 新版任务面板（文件通道自 v0.4.0 加入）。旧“单脚本兼容入口”保持文字收发，不启用此通道。功能与验证范围见[统一清单](功能清单与验证状态.md)。

## 第一次体验

1. 电脑打开新版面板并“连接手机”，保持开机联网。
2. 在手机 QQ 中当前已连接的个人账号会话直接发送一份小 TXT 文件，不需要附加 `/py` 文字。
3. 等待收到“附件已保存：inbox/…文件名.txt”。接收中还不能立即处理，先等待保存确认。
4. 发 `/py 菜单`，选“选择文件进行处理或取回”→该文件→“生成并回传 TXT 概览报告”。也可按原始指令发送 `/py 运行 fileinfo inbox/实际文件名.txt`。
5. 电脑读取文件概况，生成“文件概览.txt”，随后作为 QQ 附件回传。报告是统计和少量预览，不是 AI 总结全文。

手机文件按独立编号存进电脑共享目录的 `inbox/`，同名不同消息不会覆盖。手机图片也会保存，图片不是自动送给 AI。上传文件不触发执行、解压或自动运行工作程序。

## 手机常用指令

| 指令 | 效果 |
|---|---|
| `/py 菜单 文件` | 完整文件用法与限制 |
| `/py 文件` | 列出共享文件，包括 inbox/ 和 results/ 内的文件，最多 100 个 |
| `/py 运行 inspect 实际共享文件名` | 只看文字概况 |
| `/py 运行 fileinfo 实际共享文件名` | 生成 TXT 概览报告，自动作为附件回传 |
| `/py 发文件 实际共享文件名` | 将共享目录内的文件作为原格式附件发回 |
| `/py 发图片 实际共享图片名` | 将支持的图片直接显示在会话里 |

相对文件名可以包含空格，整段复制即可；不用加引号。手机上的路径不是电脑路径。文件指令不允许绝对路径、上级路径、隐藏文件或指向共享目录外的链接。

“发文件”始终按附件发送，包括图片；“发图片”支持 PNG、JPEG、GIF、WebP，并检查图片头。自动回传时，小图片以图片消息发送，其他内容作为文件附件。PDF、Word DOCX、Excel、PPTX、RTF、HTML 和常见文本已接入统一读取器；PDF/Excel/RTF 需在电脑安装读取组件。手机用 `/py 格式` 查看组件状态，详见[文件格式读取说明](文件格式读取说明.md)。压缩包等仍只传输，不自动解压或执行。

## 把文件交给自己的程序

在电脑“添加本机工具”中登记可信程序。启动参数每行一个：

- `{text}`：本次手机文字，保持一个原样参数。
- `{file}`：把手机指定的共享相对文件名转换为电脑完整路径；不存在、超出边界或超过 50 MB 会拒绝。
- `{output}`：当前任务专用输出目录。

例如已有 `convert.py 输入文件 输出目录`，参数设置为两行：

```text
{file}
{output}
```

登记的工具 ID 假设是 `convert`，手机发送 `/py 运行 convert inbox/实际文件名.txt`。

程序也可以读取这两个环境变量：

```python
import os
from pathlib import Path

output = Path(os.environ["QQ_BRIDGE_OUTPUT_DIR"])
(output / "结果.txt").write_text("这是本次工作结果", encoding="utf-8")
```

`QQ_BRIDGE_SHARED_DIR` 是共享目录。`QQ_BRIDGE_OUTPUT_DIR` 通常为 `shared/results/任务编号/`。普通 Python、交互 Python 和已登记 CLI 都会获得这些环境变量。

任务成功结束后，桥接只检查本任务专用输出目录，最多自动加入 10 个附件。失败和取消任务不会自动回传，已有文件仍保留，可自行检查后用“发文件”取回。交互程序要真正结束后才会自动收集文件。原有程序若把结果写到别处，需要设置输出位置，或把文件放进共享目录后手动回传；不会扫描整个电脑寻找结果。普通 `print()` 输出里的路径也不会触发附件发送。

输出目录是明确的回传位置，只放准备发给手机的文件；文件内容不会自动进行密钥遮盖。

## 容量与反馈

| 项目 | 限制 |
|---|---|
| 单个接收或回传文件 | 50 MB |
| 直接显示的图片 | 10 MB |
| inbox 接收目录总量 | 500 MB；满后须自行整理 |
| 内置概况、TXT 报告和 AI 读取输入 | 常见文档/表格/文本；文字 1 MB，DOCX 10 MB，PDF/Excel/PPTX 20 MB；全文 20 万字 |
| 自动回传结果 | 每个成功任务最多 10 个 |
| 文件等待队列 | 接收和发送各最多等待 20 项 |

接收和发送使用独立工作线程，文件下载不会占用两项程序任务名额，也不会阻塞普通文字指令。文件采用流式读取，不会整个加载进内存；不允许 QQ 下载请求携带桥接连接令牌。

“附件已保存”表示文件已在电脑共享目录落盘。“已加入附件回传队列”表示开始排队。“附件已交给 QQ”表示后台返回了发送凭据，不代表手机已打开或下载。

发送回执丢失时可能实际已发送，状态记为“未确认”，不会自动重发。先查看手机，确实没收到再发“发文件”指令。重启后旧队列不重放；中断的接收和未发送请求不自动继续。发送使用暂存快照，不改动或删除原共享文件；未确认的快照和传输记录保留在本机 `.runtime/file-channel/`。

## 接收来源与兼容性

只接受带签名的当前登录账号自己的个人私聊文件事件，忽略其他联系人、群聊和启动前历史。支持私聊 file/image 消息段及 offline_file 通知。QQ 回显自己刚发送的附件时按文件或消息发送凭据过滤；回调早于上传响应时短暂等待凭据，不按文件名、大小或图片内容直接判定回声。因此手机可以重新发送刚收到的相同附件。

私聊文件通过 `get_private_file_url` 获取地址，图片通过 `get_image` 获取地址或缓存；必要时使用 `get_file`。远程下载限制为 QQ 资源域或公共 IP，拒绝本机/内网地址、任意其他网站和不安全重定向。仅使用可信本机后台 API 返回、位于允许的 QQ/NapCat 缓存根目录内的本地缓存；消息自带的电脑路径不会被读取。自定义缓存位置未在允许范围时可能接收失败，优先使用能返回 QQ 下载 URL 的后台。

文件回传使用 NapCat 的 `upload_private_file`，图片使用 `send_private_msg` 的 image 消息段。依据 [NapCat 文件处理文档](https://napneko.github.io/develop/file)、[扩展 API 文档](https://napneko.github.io/develop/api/doc) 与本机固定版本 4.18.41 的实现核对。此版本只支持和后台运行在同一台电脑的部署方式。

已在本机与真实手机 QQ 验证 TXT 和图片发送、接收及原始内容一致性。处理报告的自动回传与手机指令取文件的验收进度见 [验证记录](validation.md)。50 MB 大文件、不同手机与长期运行尚未实测。
